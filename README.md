# O-Alarm

Alarm + wake app for iOS and Android: _set when you need to wake up; the app makes sure you do._
Product brief: [`docs/PRODUCT.md`](docs/PRODUCT.md). Binding architecture decisions: [`docs/DECISIONS.md`](docs/DECISIONS.md).

Expo SDK 57 · React Native 0.86 (New Architecture) · Expo Router (typed routes) · TypeScript strict ·
NativeWind 4 · expo-sqlite + Drizzle · Jest (jest-expo).

## Running the app

```sh
npm install
npx expo start
```

There are two ways to run it, and they behave differently on purpose (D6):

|              | Expo Go (preview)                                                | Development build                                                                                                                             |
| ------------ | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| How          | Scan the QR code from `npx expo start` with Expo Go (latest SDK) | `npx expo run:android` (local, needs Android SDK + JDK 17) or an EAS build (`npx eas-cli build --profile development`; iOS is cloud-only, D7) |
| Alarm engine | `PreviewAlarmEngine` — in-memory JS                              | Native module `modules/alarm-engine`                                                                                                          |
| Alarms ring? | **No.** A persistent banner says so on every screen              | Yes, once the native engine ships (it currently rejects every call with `NOT_IMPLEMENTED`, and the app shows the alarm as _Not scheduled_)    |

Everything else (local database, create/edit/delete, next alarm, diagnostics) works the same in both.
The engine is picked at runtime by `resolveEngine()` in `src/engine/resolve-engine.ts`: native when
the module is linked and the app isn't running in Expo Go, preview otherwise. The native module is
optional at runtime, so Expo Go never crashes on it.

`ios/` and `android/` are generated by `npx expo prebuild` (Continuous Native Generation) and are not
committed. Configure native behavior in `app.config.ts` and config plugins.

## Layout

```
app/                       Expo Router routes — thin; each renders a feature screen
  (tabs)/                  Native tabs: (home) Alarms, bedtime, insights, settings (+ diagnostics)
  alarm/new.tsx, [id].tsx  Create / edit (modal)
  ringing, mission, wake-check, paywall
src/domain/                Pure TS, no React/Expo: alarm model (D9), recurrence + DST, snooze,
                           mission types/registry contract, wake-check reducer, event union
src/engine/                AlarmEngine contract, PreviewAlarmEngine, NativeAlarmEngine adapter,
                           resolveEngine (D6), reconcile (DB ↔ engine diff/apply/verify, D10)
src/db/                    Drizzle schema, bundled migrations, repositories,
                           alarm-service.ts (the D11 write path)
src/features/<feature>/    Screens + feature logic (alarms, ringing, missions, wakecheck, sleep,
                           insights, paywall, settings, diagnostics)
src/components/            Shared UI (Screen, PreviewBanner, Section, ListRow, Button, …)
src/lib/app-services.tsx   Boot: open DB, resolve engine, reconcile on start/foreground/tz change
src/theme/tokens.ts        JS mirror of the color tokens in global.css (parity-tested)
modules/alarm-engine/      Local Expo module: TS API + Swift/Kotlin stubs (native engine is next)
supabase/                  Backend (owned separately)
```

## Key flows

- **Write path (D11)** — `alarmService.save()` persists the alarm + an `alarm_created/updated`
  event, schedules it through the engine, reads the engine back to verify, logs
  `alarm_native_scheduled` or `alarm_schedule_failed`, enqueues an outbox row for sync, then
  notifies the UI. A scheduling failure keeps the alarm saved locally, shows it in the UI and in
  Settings → Alarm reliability.
- **Reconciliation (D10)** — `reconcile(alarms, engine)` computes the next two occurrences per
  enabled alarm, keyed by `occurrenceKey = <alarmId>@<local date>`, and diffs them against
  `engine.getScheduled()`: schedules what's missing, reschedules drift, cancels orphans and
  duplicates, then verifies the read-back. Running it twice changes nothing.
- **Time (D9)** — wall-clock alarms, floating or fixed-zone. DST gap → first valid instant after
  the gap; DST overlap → first occurrence. See `src/domain/recurrence.test.ts`.

## Styling

Semantic color tokens (`background`, `surface`, `foreground`, `accent`, `danger`, `warning`, …)
are CSS variables in `global.css` with light/dark values, exposed as Tailwind colors. Type uses
the HIG scale (`text-large-title` … `text-caption`, plus `text-display` for alarm times). Contrast
(WCAG AA, body text ≥ 7:1) is checked in `src/theme/tokens.test.ts`. Native controls (switches,
time picker) come from `@expo/ui`, which also runs in Expo Go.
