# O-Alarm backend (Supabase)

Postgres schema, RLS, analytics views and tests for cloud sync, history, AI and billing state
(`docs/DECISIONS.md` D15–D19). **Nothing here is on the alarm ring path**: alarms are local-first and
must work with Supabase, Clerk, OpenRouter and RevenueCat all down (`docs/PRODUCT.md`).

## Layout

```
supabase/
  config.toml                 CLI config (Clerk third-party auth, see below)
  .env.example                env vars for local runs (no secrets)
  migrations/                 versioned SQL, applied in filename order
  tests/database/*.test.sql   pgTAP tests (RLS, anon denial, read-only, constraints, views, functions)
```

Edge Functions (OpenRouter, RevenueCat webhook) are not part of this change; they will live in
`supabase/functions/` and write to the service-role-only tables below.

## Schema overview

| Table | Who writes | Notes |
|---|---|---|
| `users` | client (own row) | PK `id` = Clerk user id (`auth.jwt()->>'sub'`). Must exist before a user's other rows (FK). |
| `devices` | client | platform, versions, tz, `alarm_engine` (`native`/`preview`), `readiness` diagnostics snapshot. |
| `alarms` | client | Schedule is **folded in** (hour/minute/`weekdays` ISO 1–7 or `one_time_date`, `timezone_policy`, skip/override), plus snooze, `mission_chain jsonb`, Wake Check config. |
| `alarm_occurrences` | client | Expected vs observed: `expected_at`, `native_scheduled_at`, `triggered_at`, `dismissed_at`, `snooze_count`, `outcome`. Unique `(user_id, alarm_id, occurrence_key)`. |
| `wake_sessions` | client | Ring → confirmed-awake flow, 1:1 with an occurrence. |
| `missions` | migrations / service role | Global catalog (math, shake, steps, qr + planned types), `tier` free/pro. Read-only to clients. |
| `mission_attempts` | client | Per attempt: type (FK to catalog), chain `position`, `purpose`, outcome, timing. |
| `wake_checks` | client | Post-dismissal verification, `outcome`, `retriggered`. |
| `sleep_sessions` | client | Night/nap, generated `duration_minutes`. |
| `morning_checkins` | client | `energy` 1–5, `sleep_quality` 1–5; one per user per `local_date`. |
| `preferences` | client | One row per user (`on_conflict=user_id`): sleep goal, bedtime, reminders, `ai_personalization_enabled`. |
| `ai_insights` | **service role only** | `type`, period, `structured jsonb`, `explanation`, `model`. Client read-only. |
| `entitlements` | **service role only** | RevenueCat mirror (`pro`). Client read-only. |
| `sync_state` | client | Per-device pull cursor, `guest_migrated_at`. |
| `events` | client, **append-only** | `name` is checked against the 15 PRODUCT.md key events. |
| `data_export_requests` | client creates, service role progresses | Async export jobs. |

**Why no `alarm_schedules` table:** D9 gives every alarm exactly one wall-clock rule, so a separate
table would be a 1:1 child costing an extra join, tombstone and version per alarm. Concrete fire
instants already have their own table (`alarm_occurrences`). Split it out only if multi-rule alarms ship.

### Sync conventions (every syncable table)

- `id uuid` PK generated by the client, `user_id text` (Clerk id), `device_id uuid`, `created_at`,
  `updated_at`, `version bigint`, `deleted_at` (soft-delete tombstone). Index `(user_id, updated_at)`.
- `updated_at` and `version` are **server-managed** by the `sync_touch` trigger (client values are
  ignored): `version` is 1 on insert and +1 per update; `updated_at` is `clock_timestamp()`. `id`,
  `user_id` are immutable. Conflict policy is last-writer-wins per row (D17).
- Pull: `where user_id = $me and updated_at > $cursor order by updated_at`. Commits are not strictly
  ordered by `clock_timestamp()`, so re-read with a small overlap (e.g. cursor − 5 s); writes are idempotent.
- Clients **soft-delete** (`update … set deleted_at`); there is no client `DELETE` grant. Hard deletion
  is `delete_my_data()`.
- Children reference parents with composite `(parent_id, user_id)` FKs (a row can never point at another
  user's parent). FKs are `DEFERRABLE INITIALLY DEFERRED`: push parents and children in one transaction/RPC
  in any order; across separate requests push parents first (`users` → `alarms` → `alarm_occurrences` →
  `wake_sessions` → `mission_attempts`/`wake_checks`).
- Natural keys are unique (`occurrence_key`, one session per occurrence, one check-in per day,
  one `preferences` row). Derive the row `id` deterministically (uuid v5 of the key) so two devices
  converge on the same row instead of hitting a unique violation.
- `events` has only `id`, `user_id`, `device_id`, `created_at`, `name`, `occurred_at`, ids, `properties`:
  no `updated_at`/`version`/`deleted_at` because rows are never modified. Insert with
  `on conflict (id) do nothing`. Keep raw sleep data out of `properties`.
- `ai_insights`/`entitlements`/`data_export_requests` carry the same sync columns so they can be pulled,
  but `device_id` is null (no device writes them). Webhook/Edge Functions must upsert `users` first.

### Security model

- RLS is on for every table. Policies are `to authenticated` with
  `(select auth.jwt()->>'sub') = user_id` (`users`: `= id`). `anon` has **no** privileges on any table, view
  or function (grants revoked, default privileges changed) — and no policies.
- Clients get `select, insert, update` only (`events`: `select, insert`; `ai_insights`, `entitlements`,
  `missions`: `select`). `service_role` (Edge Functions) bypasses RLS.
- Pro gating is **not** enforced in SQL (the brief makes cloud sync a Pro feature, but that is a product
  call; an `entitlements`-based check can be added to the write policies later).
- `export_my_data()` returns the caller's rows as one jsonb document; `delete_my_data()` hard-deletes the
  caller's `users` row (cascade removes everything, events included) and returns per-table counts. Both are
  `SECURITY DEFINER`, scoped to the JWT `sub`, raise for callers without one, and are not executable by anon.
  Deleting the Clerk user and the RevenueCat subscriber is **not** SQL: do it from an Edge Function after
  `delete_my_data()`.
- Tests fail if a public table lacks RLS, if anon can touch anything, or if a user-owned table is missing
  from `user_data_tables()`.

### Analytics views (`security_invoker = true`, RLS applies to the caller)

`analytics_wake_success_weekly`, `analytics_avg_snoozes_weekly`, `analytics_mission_effectiveness`,
`analytics_mission_chain_effectiveness`, `analytics_wake_check_failure_weekly`,
`analytics_weekday_difficulty`, `analytics_sleep_vs_energy`. Weeks are ISO weeks of `local_date`.
"Wake success" = occurrence `dismissed` and its wake session (if any) `success`; skipped, cancelled,
pending and still-active sessions are excluded. Ratios are 0..1.

## Run locally

Requires Docker. The CLI is not a repo dependency; use `npx`:

```sh
npx supabase@latest start          # applies supabase/migrations
npx supabase@latest db reset       # re-apply from scratch
npx supabase@latest test db        # pgTAP tests in supabase/tests/database
npx supabase@latest db lint        # plpgsql lint, expect "No schema errors found"
npx supabase@latest stop
```

Local API: `http://127.0.0.1:54321`, DB: `postgresql://postgres:postgres@127.0.0.1:54322/postgres`
(`start` prints the local keys). The tests simulate Clerk by setting the `request.jwt.claims` GUC,
so they need no Clerk instance. Add a migration with `npx supabase@latest migration new <name>`.

## Clerk setup

1. **Clerk Dashboard → Integrations → Supabase** (or Configure → Sessions → customize session token): activate
   the integration for your Clerk instance. This makes session tokens carry `"role": "authenticated"`,
   which Supabase needs to map the token to the `authenticated` Postgres role. Note the **Clerk domain**
   (Frontend API URL without scheme, e.g. `your-app-12.clerk.accounts.dev`).
2. **Hosted Supabase project:** Dashboard → Authentication → Sign In / Up → Third-party → *Add provider* → Clerk,
   paste the domain. (Or set `[auth.third_party.clerk]` `enabled = true` and `domain` in `config.toml`
   and run `supabase config push`.)
3. **Local Supabase with real Clerk (optional):** copy `.env.example` to `supabase/.env`, set `CLERK_DOMAIN`,
   and set `enabled = true` under `[auth.third_party.clerk]` in `config.toml` (don't commit it). It is `false`
   in the repo because `supabase start` fetches `https://<domain>/.well-known/openid-configuration` at
   boot and would refuse a placeholder domain, breaking start/tests for everyone without a Clerk instance.
4. **App:** create the Supabase client with the Clerk token, e.g.
   `createClient(url, publishableKey, { accessToken: async () => (await getToken()) ?? null })`
   (`getToken` from `@clerk/clerk-expo`'s `useAuth`; no `template` argument, the native integration uses the
   default session token). After sign-in, upsert the caller's `users` row (`id` = Clerk user id), then sync.

## Environment variables

No secrets in git (D21).

| Where | Name | Purpose |
|---|---|---|
| `supabase/.env` or shell (CLI) | `CLERK_DOMAIN` | Clerk Frontend API domain; only needed if Clerk is enabled in `config.toml`. |
| App (`EXPO_PUBLIC_*`, publishable) | `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` | Client config. |
| Edge Functions secrets (`supabase secrets set`) | `SUPABASE_SERVICE_ROLE_KEY` (injected by Supabase), `OPENROUTER_API_KEY`, `REVENUECAT_WEBHOOK_AUTH`, `CLERK_SECRET_KEY` (account deletion) | Server side only, never in the client. |
